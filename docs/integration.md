# 接入现有 Cedar / Nebula

本仓库是独立库，不包含 Nebula 源码。下列为接入设计，尚未在 Ubuntu 或真实模型上联调。

## 生命周期

1. 应用启动阶段从配置获取数据库绝对路径，构造 MemoryStore；启动失败由业务决定拒绝启动或显式关闭记忆，不静默丢数据。
2. 业务已有 SessionStore 继续负责最近对话和 pending；SDK 不新增第二份 SessionStore。
3. 服务端绑定生成 scope，入口映射产生 session_id。匿名用户使用临时隔离 scope，不共享个人记忆。
4. 记忆 I/O 通过 CedarMemory 异步方法调用，不在 import 阶段初始化。
5. scope/key 写操作按业务顺序执行，同一 scope 的删除与模型生成建议串行。不同进程由 SQLite 事务保证写一致性，不保证业务请求到达顺序。

## 模型调用前

- 当前轮判断需要哪些偏好，例如 lighting.preference，再传 keys 召回；不要无条件 list 全部偏好注入。
- 当前指令优先，记忆只是有来源的背景，不提升为新的 system 指令。
- 把 context 作为标记清楚的数据块，通过现有提示词模板接入；不改写原有模型协议。
- 字符限制之外，业务还须按实际模型 token 窗口控制总上下文。
- 同一记忆不要既注入旧 YAML 画像又注入相冲突的新记录；业务选择最新明确偏好，并确定静态画像的覆盖规则。

## 模型调用后

- 明确的保存/更新请求经过业务确认后写入。SDK 不解析“如果我喜欢冷光”一类假设句。
- 会话达到摘要阈值时，按连续新增轮次调用 summarize。模型回调只生成文本，不执行工具。
- 工具失败和状态未知必须在摘要中保留，不得总结为“已完成”。摘要不作为设备真值。
- 首版无自动定时任务：业务决定何时调用，避免阻塞实时首字返回。

## 忘记与更新

删除偏好会在同一事务内递增 scope revision、清除摘要。删除期间已在运行的旧摘要回调即使完成，也无法用旧 revision 写回。

还必须由业务完成：清理旧 Session 历史、缓存、旧画像副本、已经生成的上下文以及摘要输入队列。重置摘要累计轮次，避免旧历史再次进入模型。SDK 无权访问或清理这些外部状态。

`clear_summary` 首版也会清除同 scope 的其他摘要，这是缺少细粒度依赖图时的保守行为。不将它用于正常每轮裁剪。

## 持久化和部署

- SQLite 文件存入 Ubuntu 的持久目录，不放入镜像层或 Git。
- 只用于本机磁盘；不可把 WAL 数据库放在跨主机共享目录上冒充多 Station 同步。
- 设置目录访问权限和容量告警。当前无数据 TTL、自动备份、远端同步或后台清理。
- 热备份应使用 SQLite backup API 或可靠的停写备份流程，不仅复制主 db 而漏掉 WAL。
- 更新前备份；当前仅支持 schema v1，遇到其他版本报错，不静默重建或覆盖。

## 最小验收清单

显式保存 → 相同 scope 新会话召回 → 重启召回 → 更新覆盖 → 忘记后查询为空 → 旧摘要失效 → 两个 scope 不串数据。

再补：模型回调超时不生成新摘要、删除和摘要并发不复活旧结果、存储不可用不报告保存成功、重复确认不从记忆触发设备执行（最后一项由业务 Session 测试负责）。
